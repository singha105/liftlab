## Hypothesis

> Because we see that a first-time visitor has to make three choices (length, optional goal, Start) before the timer runs, and starting is where we expect the biggest loss (about half of new users never start), we believe a one-click "Start a 25-minute focus" button for new users will increase activation rate.

Day 3's synthetic funnel puts numbers on that loss: 50.5% of new users never start a sprint in their first 24 hours, the largest drop-off of the four steps. That figure comes from the backlog's own assumptions, so it motivates the test rather than proving the problem exists.

## Design

| | |
|---|---|
| Unit of randomization | The anonymous PostHog `distinct_id`: one browser on one device. PostHog hashes it with the flag key, so a user keeps their arm on every visit. |
| Allocation | 50% control, 50% test |
| Eligibility | New users only: the page load that is this device's first ever StudySprint open (`is_first_open: true`). Demo mode (`?demo=1`) is never enrolled. |
| Control | The current start screen, unchanged. |
| Test | While the user hasn't started a session, the start screen shows one large "Start a 25-minute focus" button. The length picker and goal chips sit behind "Customize length or goal", which opens the normal screen. Quick Start runs 25 minutes with no goal and sends `start_method: quick_start`. Once a session has started, the user sees the normal screen. |

### Exposure

A user is exposed when all of these hold:

1. This page load is their first open on the device.
2. PostHog loaded and returned `control` or `test` for `exp-001` within 1.5 seconds.
3. At that moment they're still on the start screen and haven't touched it: no session started, no length or goal picked.

Then `experiment_exposed` fires once, with `experiment_key: exp-001` and the variant, and the arm is saved on the device. In the test arm, this is the moment the screen switches to Quick Start. In control nothing on screen changes, but exposure fires at the same point.

Every condition is checked before the arm is known, so the two arms are filtered the same way. A user whose flag doesn't load in time (ad blocker, slow network, Do Not Track) sees control and is not exposed. They're left out of the analysis rather than counted as control, which would make the control arm bigger than the test arm and bias the comparison.

A known cost: a test user sees the normal screen for up to 1.5 seconds before Quick Start replaces it. The alternative was to hold back the start screen until the flag loads, but that would change the control experience, and control has to be the current app.

## Metrics

All definitions follow [METRICS.md](../METRICS.md). The population is every exposed user whose 24-hour activation window has closed. Users exposed to both arms (possible only through a bug) are dropped, and their number is reported.

| Role | Metric | Definition | Test |
|---|---|---|---|
| Primary | Activation rate | Share of exposed users with a `session_completed` within 24 hours of their first `app_opened`. | Two-sided z-test for the difference test − control, with a 95% Wald confidence interval. |
| Secondary | Sessions per user in 7 days | Completed sessions per exposed user in the 7 days after their first `app_opened`, zeros included. Completed rather than started, because Quick Start raises starts by design and this is the North Star counted per user. | Welch t-test for the difference in means, with a 95% confidence interval. |
| Guardrail | Abandon rate | Sessions started by exposed users in their first 7 days that end in `session_abandoned`, or have no end event 24 hours after they start, ÷ those sessions that ended. Sessions are grouped within users, so the CI uses the delta method with the user as the unit. | Regresses beyond its threshold if test − control is above **+2.0 percentage points**. |
| Guardrail | Page load time | p75 of `load_ms` on `app_opened` events from exposed users after their exposure page load, within 7 days. The exposure load itself is measured before the flag arrives, so it can't differ by arm; later loads are where the test screen renders at startup. | Regresses beyond its threshold if test p75 is more than **10% above** control p75, or above **2,000 ms**. |

A guardrail is judged on its point estimate, with its confidence interval reported next to it. With the sizes below, the abandon-rate difference has a standard error of about 1.4 points (delta method on the Day 3 synthetic data, about 2 ended sessions per user in the first week). So if Quick Start doesn't change abandon rate, the point estimate still lands above +2.0 about 8% of the time. That false-alarm rate is accepted, since quietly raising abandon rate is this test's main risk.

Exploratory only, with no say in the decision: start rate, D1 retention (both from the backlog), and the share of test-arm starters whose first session has `start_method: preset`, meaning they went through "Customize". There's no event for opening Customize, and the tracking plan doesn't get one for this.

## Sample size

| Input | Value |
|---|---|
| Baseline activation | **30.0%**: Day 3 funnel, `session_completed` overall conversion, 5,069 of 16,881 new users. **Synthetic**, from the backlog's assumed ~30%. |
| MDE | **+5.0 percentage points absolute** (30.0% → 35.0%, +16.7% relative) |
| Alpha | 0.05, two-sided |
| Power | 0.80 |
| **Required** | **1,377 exposed users per arm, 2,754 in total** |

From `uv run liftlab power --baseline 0.30 --mde 0.05`, which matches statsmodels' `power_proportions_2indep`.

Why +5 points: it's roughly the lift the backlog's impact score assumed for removing two of three choices at the biggest leak. Smaller lifts would be worth shipping too, since Quick Start costs nothing to keep. But detecting +3 points needs 3,763 users per arm, 2.7 times as many. So we accept that a true lift of 2 or 3 points will probably end as ITERATE rather than SHIP.

At this sample size, the secondary metric can detect a change of 0.24 completed sessions per user in 7 days (+17.5% on the synthetic baseline of 1.40, sd 2.29). The guardrails aren't powered on their own; they're there to catch large regressions.

## Duration and feasibility

Every user in the 2,754 has to be new, load PostHog, and get their flag within 1.5 seconds.

| Eligible new users a day | Days to reach 2,754 |
|---|---|
| 5 | 551 |
| 10 | 276 |
| 40 | 69 |
| 100 | 28 |

StudySprint's realistic traffic is about **5 eligible new users a day**, and that's generous. It's a portfolio project on GitHub Pages with no marketing, and ad blockers and Do Not Track remove some visitors before they're ever eligible. At that rate the experiment needs about a year and a half.

**StudySprint can't reach N.** The live run is capped at 8 weeks and will almost certainly end underpowered: at 5 a day, 8 weeks gives about 140 users per arm. That can only detect a lift of around 16 points.

So the work is split:

- **The statistics** are validated where the answer is known. That means the Day 3 simulator, which generates experiments with a known true effect (before launch, the test is run 200 times at this N with a true +5-point effect, and should detect it about 80% of the time), and the public Cookie Cats A/B test on Day 6, with about 90,000 players.
- **The live run** proves the plumbing on real browsers: the flag assigns about 50/50, `experiment_exposed` fires once per user with the right variant, Quick Start sessions arrive as `start_method: quick_start`, and the export → warehouse → SQL path produces the per-arm tables. Its activation numbers get reported, labeled underpowered, and not acted on.

## Analysis plan

Run in this order. The analysis of record is the warehouse SQL on events exported from PostHog (`source = 'posthog'`). PostHog's own experiment view is a live monitor only.

1. **Sample ratio mismatch.** A chi-square test of exposed users per arm against 50/50. If p < 0.001 the run is invalid: no decision is made, the cause gets found and fixed, and the test restarts with fresh assignment.
2. **Primary.** Activation rate by arm, the difference with its 95% CI, and the p-value. This is read once, when both arms reach 1,377 exposed users with closed windows, or at the 8-week limit.
3. **Guardrails.** Abandon rate and page load p75 by arm, with differences and CIs.
4. **Secondary.** Completed sessions per user in 7 days by arm, with the difference and its CI.
5. **Variance reduction (CUPED).** It doesn't apply here. CUPED adjusts with each user's pre-experiment behavior, and a new user has none. Day 5's CUPED is validated on the simulator's returning-user experiments for later tests. As a sensitivity check only, the primary is re-estimated with regression adjustment on two attributes fixed before exposure: `$device_type` and `referrer_type`. The decision uses the unadjusted estimate.
6. **Sequential monitoring.** The primary is not looked at before the read in step 2, so the fixed-horizon alpha of 0.05 holds. SRM and the guardrails are checked weekly, and the run can be stopped early only for an SRM failure or a guardrail regression. Once Day 5's sequential test is in the stats library, the weekly guardrail checks use it.

## Decision rule

Applied once, at the read in step 2, top to bottom. The first condition that matches decides.

1. **INVALID** if the SRM check fails (p < 0.001). No decision.
2. **UNDERPOWERED** if the 8-week limit arrives before 1,377 exposed users per arm. No decision; the product stays on control and the estimates are reported as such.
3. **KILL** if any guardrail regresses beyond its threshold: abandon rate test − control above +2.0 points, or page load p75 in test more than 10% above control or above 2,000 ms.
4. **SHIP** if the 95% CI for the activation difference (test − control) is entirely above 0, and the 95% CI for sessions per user in 7 days is not entirely below 0.
5. **ITERATE** if the activation point estimate is at least +2.5 points (half the MDE). That includes a significant activation win that fails rule 4 only because week-one sessions dropped.
6. **KILL** otherwise.

SHIP means Quick Start becomes the default for new users. ITERATE means a follow-up test of a revised version, pre-registered separately. KILL means the flag is turned off and Quick Start is removed.

## Amendments

### 1. 2026-10-31, before launch: how the weekly checks use the sequential test

Step 6 said the weekly guardrail checks would use Day 5's sequential test once it existed, but not how. Written down before any data arrives; the primary metric, the read and the decision rule don't change.

- A look every 7 days from launch. SRM is checked on everyone exposed so far, with the same chi-square test and p < 0.001 threshold as the read.
- Each guardrail is computed on users whose 7-day window had closed by the look (exposed at least 8 days earlier), and followed as an mSPRT 95% confidence sequence over the looks so far (Johari, Pekelis and Walsh, [arXiv:1512.04922](https://arxiv.org/abs/1512.04922)). The normal mixing distribution's sd is the guardrail's own threshold: 2.0 points for abandon rate, 10% for the relative p75, and 200 ms (10% of the cap) for the test arm's p75.
- The run stops early only for an SRM failure (INVALID) or a guardrail whose always-valid interval lies entirely beyond its threshold (KILL, rule 3). During the run, a point estimate past the threshold isn't enough on its own, because it would be checked about 8 times. At the read, rule 3 applies as written.

`uv run liftlab monitor --source posthog` runs these checks.
